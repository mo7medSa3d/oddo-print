# Distributed Tracing — OTel-Inspired Correlation IDs

## Overview
Enterprise observability requires tracing a print job across Odoo → Gateway → Queue → Agent → Printer → Spooler.

**Current implementation is OTel-inspired distributed correlation, NOT full OpenTelemetry compliance.** No OTel SDK, no trace spans, no OTLP exporter yet. Custom fields are application-specific, not official OTel semantic conventions.

## Correlation IDs (Application-Specific Fields)
These are custom application fields, documented as such:
- `requestId` / `request_id`: per HTTP request, from `X-Request-Id` or generated `req_<nanoid>`. Propagated via header. Application-specific, not `http.request_id` OTel.
- `jobId` / `job_id`: print job ID (`job_...` or `cert_...`). Application-specific, not official OTel `job.id`.
- `tenantId` / `tenant_id`: tenant isolation key. Application-specific.
- `agentId` / `agent_id`: agent owner. Application-specific.
- `printerId` / `printer_id`: printer target. Application-specific.
- `attemptId` / `attempt_id`: delivery attempt (`attempt_<nanoid>`), incremented per claim. Application-specific, not OTel.
- `claimId` / `claim_id`: redacted claim reference (sha256 hash), fenced ownership — raw token never exposed. Application-specific.
- `spoolerJobId` / `spooler_job_id`: Windows spooler job ID when using spooler transport (Gateway↔Spooler linking). Application-specific.

Logs are JSON lines with these fields. Future: export to OTel collector via OTLP with proper semantic conventions.

## Implementation

### Gateway (Next.js)
- `src/server/correlation.ts`: AsyncLocalStorage for correlation context, generates requestId, attemptId, claimId
- `src/lib/log.ts`: automatically enriches logs with correlation context from AsyncLocalStorage, sanitizes sensitive keys
- Middleware: `requestIdFrom(req)` extracts or mints request ID, `X-Request-Id` header returned in all responses
- APIs: `/api/jobs/[id]/timeline` returns correlation object with REDACTED claimId (never raw token), `/api/printers/[id]/certify` returns requestId/attemptId
- Job creation: `print-job-service.ts` records timeline events with requestId via canonical pipeline
- Agent delivery: `agent/jobs` PATCH persists `spoolerJobId` and records timeline with attemptId/redacted claimId/spoolerJobId

### Go Agent
- Should include `X-Request-Id`, `X-Job-Id`, `X-Attempt-Id`, `X-Claim-Id` (redacted), `X-Spooler-Job-Id` headers in status updates
- On spooler transport, after `OpenPrinter` + `StartDocPrinter`, capture spooler job ID via `GetJob` or `JobId` return and report back to Gateway PATCH as `spoolerJobId`
- Logs include correlation IDs (application-specific)

### Tauri Desktop Manager
- `gateway_request` command validates origin same scheme/host/port, method allowlist, header budget 64KiB, body 8MiB
- Forwards `X-Request-Id` header
- UI shows correlation IDs in JobTimeline and CertificationWizard (redacted claimId)

### Odoo Addon
- When creating print job via JSON-2 Bearer API, include `X-Request-Id` header generated by Odoo
- Store `request_id` in print job record for traceability
- Gateway stores Odoo's request_id in `print_jobs.request_id`

## Timeline Stages
Real Print Certification wizard steps map to timeline stages (state-driven from job row):
- Gateway: job created (observed)
- Auth: tenant/printer ownership verified (observed)
- Queue: job enqueued via canonical pipeline with idempotency (observed)
- Claim: agent claim via advisory lock + claim_token — observed from job status (queued→pending, claimed→ok)
- Agent: agent claimed job — observed, not inferred from lastSeenAt
- Transport: RAW/IPP/Spooler selected — observed from job status >= claimed
- Physical: paper verification — BLOCKED if no hardware, never auto-ok
- Ack: agent ack success — observed from job status success/failed
- Final: certification complete — pending if waiting, blocked if blocked steps, never auto-certified

Timeline table `job_events`:
- `stage`: created/queued/claimed/accepted/connection/printing/delivery/success/failed/expired/blocked
- `status`: ok/error/blocked/pending
- `attempt_id`, `claim_id` (redacted), `spooler_job_id` for linking
- `request_id` for request tracing

## Usage for Client Demo
1. Create job via Odoo or `/api/print` with `X-Request-Id: demo-123`
2. Check logs: `grep demo-123 gateway.log` shows full trace with application-specific fields
3. Check timeline: `GET /api/jobs/<id>/timeline` returns events with correlation, claimId redacted
4. Check spooler linking: `spoolerJobId` field in job row + timeline events
5. Certification: `POST /api/printers/<id>/certify` returns steps with requestId/attemptId and BLOCKED handling, state-driven
