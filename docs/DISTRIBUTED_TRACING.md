# Distributed Tracing — Correlation IDs

## Overview
Enterprise observability requires tracing a print job across Odoo → Gateway → Queue → Agent → Printer → Spooler.

## Correlation IDs
- `request_id`: per HTTP request, from `X-Request-Id` or generated `req_<nanoid>`. Propagated via header.
- `job_id`: print job ID (`job_...` or `cert_...`)
- `tenant_id`: tenant isolation key
- `agent_id`: agent owner
- `printer_id`: printer target
- `attempt_id`: delivery attempt (`attempt_<nanoid>`), incremented per claim
- `claim_id`: claim token (`claim_<nanoid>` or UUID), fenced ownership
- `spooler_job_id`: Windows spooler job ID when using spooler transport (Gateway↔Spooler linking)

## OpenTelemetry Semantic Conventions
We follow OTel naming where possible, but lightweight (no external collector required for demo):
- `http.request_id`, `job.id`, `tenant.id`, `agent.id`, `printer.id`, `job.attempt`, `job.claim`, `spooler.job_id`
- Logs are JSON lines with these fields
- Future: export to OTel collector via OTLP

## Implementation

### Gateway (Next.js)
- `src/server/correlation.ts`: AsyncLocalStorage for correlation context, generates requestId, attemptId, claimId
- `src/lib/tracing.ts`: helpers `traceInfo`, `traceWarn`, `traceError`, `buildTraceHeaders`
- `src/lib/log.ts`: automatically enriches logs with correlation context from AsyncLocalStorage
- Middleware: `requestIdFrom(req)` extracts or mints request ID, `X-Request-Id` header returned in all responses
- APIs: `/api/jobs/[id]/timeline` returns correlation object, `/api/printers/[id]/certify` returns requestId/attemptId
- Job creation: `print-job-service.ts` records timeline events with requestId
- Agent delivery: `agent/jobs` PATCH persists `spoolerJobId` and records timeline with attemptId/claimId/spoolerJobId

### Go Agent
- Should include `X-Request-Id`, `X-Job-Id`, `X-Attempt-Id`, `X-Claim-Id`, `X-Spooler-Job-Id` headers in status updates
- On spooler transport, after `OpenPrinter` + `StartDocPrinter`, capture spooler job ID via `GetJob` or `JobId` return and report back to Gateway PATCH as `spoolerJobId`
- Logs include correlation IDs

### Tauri Desktop Manager
- `gateway_request` command validates origin same scheme/host/port, method allowlist, header budget 64KiB, body 8MiB
- Forwards `X-Request-Id` header
- UI shows correlation IDs in JobTimeline and CertificationWizard

### Odoo Addon
- When creating print job via JSON-2 Bearer API, include `X-Request-Id` header generated by Odoo
- Store `request_id` in print job record for traceability
- Gateway stores Odoo's request_id in `print_jobs.request_id`

## Timeline Stages
Real Print Certification wizard steps map to timeline stages:
- Gateway: job created
- Auth: tenant/printer ownership verified
- Queue: job enqueued (idempotency)
- Claim: agent claim via advisory lock + claim_token
- Agent: agent online
- Transport: RAW/IPP/Spooler selected
- Physical: paper verification (BLOCKED if no printer)
- Ack: agent ack success
- Final: certification complete

Timeline table `job_events`:
- `stage`: created/queued/claimed/accepted/connection/printing/delivery/success/failed/expired/blocked
- `status`: ok/error/blocked/pending
- `attempt_id`, `claim_id`, `spooler_job_id` for linking
- `request_id` for request tracing

## Usage for Client Demo
1. Create job via Odoo or `/api/print` with `X-Request-Id: demo-123`
2. Check logs: `grep demo-123 gateway.log` shows full trace
3. Check timeline: `GET /api/jobs/<id>/timeline` returns events with correlation
4. Check spooler linking: `spoolerJobId` field in job row + timeline events
5. Certification: `POST /api/printers/<id>/certify` returns steps with requestId/attemptId and BLOCKED handling
